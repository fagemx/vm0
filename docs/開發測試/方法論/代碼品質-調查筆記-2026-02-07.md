# 代碼品質調查筆記 (2026-02-07)

## 目的
- 針對「我們提交的代碼品質」做快速盤點
- 找出容易過度複雜、看起來像 AI 的風險點
- 產出可落地的簡化方向與後續方法論文件

## 盤點範圍與依據
- 以「我們可能會提交的改動」為主（測試、API routes、CLI 命令、工具模組）
- 依據：函式長度、分支密度、重複程度、資料合成步驟

## 易出現「過度複雜」的風險區塊

### 1) API Routes - 入口整合過重
- 風險：單一 handler 內包含多階段流程（驗證、DB 寫入、組裝、dispatch）
- 影響：過長、可讀性下降，容易被視為機械拼接

### 2) 資料合成流程 - 多來源 merge
- 風險：secrets/vars/credentials 合成步驟雜揉在同函式
- 影響：變更時容易誤解順序；分支過多時閱讀成本上升

### 3) 命令分派 - 分支串接長
- 風險：多段 if/else 指令分派
- 影響：擴充新命令時風格易失控

### 4) 輸入解析 - 早退 + parse 交織
- 風險：驗證與解析、分派交錯
- 影響：閱讀時需頻繁切換上下文

### 5) 路徑規則 - 白名單與例外複雜
- 風險：長條件與 nested 邏輯堆疊
- 影響：新增路徑時容易破壞既有規則

## 簡化方向摘要
- 將單一巨大函式拆成「線性步驟」：parse → validate → load → act → respond
- 用「表驅動」替代長 if/else（尤其是 command dispatch、路由判斷）
- 將多來源資料合成流程做成可讀的步驟函式（每步只做一件事）
- 減少旗標式 options，改用明確命名的 context 物件
