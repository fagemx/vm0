# 代碼品質指引

> 目標：提升「人味、簡潔、好維護」的程式風格，降低過度複雜與機械感。

## 一、核心原則

1. **線性流程優先**  
   把流程拆成清楚的步驟函式，避免單一函式塞滿多段處理。

2. **表驅動取代 if/else 長串**  
   對應命令、路由、狀態 → 用 `handlers` 表 + 預設處理器。

3. **單一步驟只做一件事**  
   每個 helper 函式只完成一個目的，不混入錯誤處理或跨層邏輯。

4. **資料合成流程明文化**  
   任何多來源 merge（env/vars/secrets/credentials）都要寫成「有順序的步驟」。

5. **少旗標、多語意**  
   避免 `options` 中塞一堆 boolean；改成清楚的 context 物件或具名函式。

## 二、改寫流程（實作步驟）

### Step 1：拆流程
把入口函式拆成：
```
parse → validate → load → act → respond
```

### Step 2：建立小 helper
- `parse*`：只做解析，不做查 DB
- `validate*`：只做驗證，不做 side effects
- `load*`：只做讀取（DB / service）
- `act*`：只做實際行為（insert / dispatch）
- `respond*`：統一組 response

### Step 3：合併回主流程
主流程應該像「導演」而不是「打工仔」：
```
const input = parseRequest(...)
validateInput(input)
const data = await loadData(input)
const result = await runAction(input, data)
return respond(result)
```

## 三、避免「AI 感」的具體寫法

### 1) 去除模板式重複
- 多次重複的 request 構造 → 變成 `makeRequest()` helper
- 多次重複的 `if/else` → 變成 `handlers` map

### 2) 命名要具體
避免「機械式」命名：
- ❌ `handleRequest`, `processData`, `runLogic`
- ✅ `parseSlackPayload`, `loadRunContext`, `dispatchRun`

### 3) 避免超長參數
- 參數超過 6 個 → 變成 `{ ... }` context
- context 裡的欄位要「可讀且可追蹤來源」

### 4) 少用微抽象
工具函式「只用一次」就不要抽。抽了反而讓讀者跑檔案。

## 四、常見區塊的改寫範式

### A. API Route
原始（過長）：
```
POST() { ... 150+ 行 ... }
```
改寫：
```
POST() {
  const input = parseRequest(...)
  validateInput(input)
  const context = await loadContext(input)
  const result = await execute(input, context)
  return respond(result)
}
```

### B. Command 分派
原始（if/else 串）：
```
if (cmd === "help") ...
if (cmd === "connect") ...
```
改寫：
```
const handlers = { help, connect, agent, ... }
return handlers[cmd] ? handlers[cmd](...) : defaultHandler(...)
```

### C. Middleware 路由判斷
原始（巨大 if）：
```
if (path.startsWith("/api") || ... ) { ... }
```
改寫：
```
if (isApiRoute(path)) { ... }
if (shouldSkipIntl(path)) { ... }
```

## 五、實際優先順序建議

1. 我們即將提交或剛改過的檔案  
2. 新增測試與 helper  
3. API routes 或 CLI commands  
4. 共用工具模組  
5. 其他零散改動

## 六、實作自我檢查清單

- [ ] 入口函式是否小於 60 行？
- [ ] 是否只有 1~2 個 early return？
- [ ] 是否能用 1 行描述每個 helper 的責任？
- [ ] 同一個 helper 是否只做 1 件事？
- [ ] 是否能看懂「資料合成順序」？

## 七、建議的落地方式

- **一次只改一個核心檔案**，避免大範圍重構
- 每次改動都留下「步驟說明」，讓 reviewer 快速理解
- 如果是多人協作：先做「示範性 refactor」建立模板，再推廣
