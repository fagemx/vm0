## 教訓 1：功能改動必須附測試 (PR #2512)

**發生了什麼：** 改了 `page.tsx` 的 `generateMetadata` 加 canonical URL，但沒寫測試就提 PR。

**根本原因：** 我們的 briefing 只涵蓋 API route 測試，`page.tsx` 的 `generateMetadata` 沒有既有測試模式可參考，就跳過了。

**教訓：** 沒有測試模式不是不寫測試的理由。如果是新類型的測試，先建立模式再寫。

**防範：**
- PR 提交前問自己：「這個改動有改到可觀察行為嗎？測試在哪？」
- 已建立 `briefing-page-level.md` 補上 page-level 測試規範

## 教訓 2：不要 mock 內部模組 (PR #2513)

**發生了什麼：** `realtime/token` 測試用了 `vi.mock("../../../../../src/lib/realtime/client")`，違反 AP-4 規則。

**根本原因：** 覺得 `realtime/client.ts` 有 `import "server-only"` 和 ably singleton 太麻煩，偷懶用了 internal mock。但實際上：
- `server-only` 已在 `setup.ts` 全域 mock
- 只要 `vi.mock("ably")` + `vi.stubEnv("ABLY_API_KEY", ...)` 就能解決

**更糟的是：** reviewer 第一次指出問題，我們只加了一行註解「解釋為什麼需要」，被打回來要求真正修掉。

**教訓：**
1. **規則違反要修掉，不是加註解合理化。** 「加 comment 解釋為何違規」是錯誤的回應方式。
2. **覺得 mock 太難時，先確認 setup.ts 已經 mock 了什麼。** 很多時候以為需要 internal mock 的情況，其實外部 mock 就夠了。

**防範 checklist（寫測試時）：**
- [ ] 所有 `vi.mock()` 路徑都是套件名（`"ably"`, `"@clerk/nextjs/server"`），沒有 `"../../"` 開頭的？
- [ ] 如果覺得必須用 internal mock，先檢查：
  - `setup.ts` 是否已 mock 了阻礙的 import（如 `server-only`）？
  - 能不能透過 mock 外部套件 + 設 env var 達到同樣效果？
- [ ] 如果真的無法避免，必須在 PR description 說明原因讓 reviewer 提前知道

### 具體解法記錄

`realtime/client.ts` 的阻礙和解法：

| 阻礙 | 以為要 internal mock | 實際解法 |
|------|---------------------|---------|
| `import "server-only"` | 會在 test 環境報錯 | `setup.ts` 已全域 mock |
| `new Ably.Rest({ key })` | 需要真的 ably instance | `vi.mock("ably")` mock 掉 |
| `process.env.ABLY_API_KEY` | 沒設會 return null | `vi.hoisted(() => vi.stubEnv(...))` |
| singleton pattern | 跨測試狀態汙染 | `mockCreateTokenRequest.mockReset()` 在 beforeEach |

## 教訓 3：測試 helper 要說明設計取捨 (PR #2508)

**發生了什麼：** `createTestDeviceCode` 用 direct DB insert，reviewer 建議加註解說明原因。

**根本原因：** 我們知道為什麼用 direct DB（API 只能建 pending codes），但沒寫在 JSDoc 裡。

**教訓：** 當測試 helper 違反常規模式（如 direct DB insert vs. 透過 API），要在 JSDoc 說明為什麼，讓後人不用猜。

**防範：** 非常規做法必須有 one-line 說明，不需要長篇大論。

## 回應 review 的正確姿勢

| reviewer 說的 | 錯誤回應 | 正確回應 |
|---------------|---------|---------|
| 「這違反規則 X」 | 加註解解釋為什麼違規 | 修掉違規 |
| 「這缺少測試」 | 「下次補」 | 這次就補 |
| 「建議加說明」 | 忽略 | 加上去，幾秒的事 |
| 「X 好像 unused」 | 直接刪 | 先確認是否真的 unused |

核心原則：**reviewer 說有問題就先假設是真的，先研究再反駁。** PR #2508 的 `agentRuns` unused 確認了確實有用才沒刪，這是正確的。

## 總防範 checklist（提 PR 前）

```
## 功能面
- [ ] 改動涉及可觀察行為？→ 有對應測試嗎？
- [ ] 測試檔名匹配來源（page.tsx → page.test.ts, route.ts → route.test.ts）？

## Mock 面
- [ ] 所有 vi.mock() 都是外部套件？沒有 "../../" 路徑？
- [ ] 需要的 env var 用 vi.hoisted(() => vi.stubEnv(...))？
- [ ] 確認 setup.ts 已全域 mock 的套件不需要重複處理？

## 文件面
- [ ] 測試 helper 的非常規做法有 JSDoc 說明？
- [ ] PR description 反映實際內容（測試數量、覆蓋範圍）？
```
